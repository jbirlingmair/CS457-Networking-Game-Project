# Server Concurrency Model Selection
I am going to select Non-Blocking I/O Multiplexing for my server. I believe this more sequential design fits the simpler facets and slow pace of Battleship. It is not necessarily a real-time application; each turn must wait for the sometimes seconds long reaction and deliberation time of humans.\
My server will have two selectors, one for each client. The server will only be able to handle a maximum of two clients at a time. Each client's socket will exist in a series of loops depending on the game state, i.e. depending whether the server is waiting for one or more clients to connect, for the Who Goes First dance, for the Ship Placing section, and finally the gameplay section where the two players actually compete against each other.\
Each event loop will only accept certain messages at certain times. There is one exception, the `DISCONNECT` message, which, depending on whether the game has started or not, either forfeits the game if the match has started and sends a `GAME_OVER` winning message to the remaining player, or restarts the match connection process from the one-player connected stage.\
Otherwise, for example, during the live gameplay section, the server will only accept a `PLAYER_TURN` message from a player if the game state is for the player's turn. Otherwise, it disregards the `PLAYER_TURN` message and sends an `ERROR` message saying "Not your turn". For a message completely out of section like `PLAYER_NUMBER`, the server ignores the message and sends an `ERROR` message saying something like "wrong time to say that".\
The server will maintain an authoritative state over the clients. The clients, if they are ever out-of-sync, can request a sync from the server to get up-to-date. The server always sends the game state to the clients whenever the game state changes. Since the players play sequentially, there is always an enforced back-and-forth between the server and clients. The clients may only change the state of the game during an approved time, like when the server is looking for a `PLAYER_NUMBER` message, or expecting a player turn input in `PLAYER_TURN`.\
The server will clean up the sockets after the game is over (i.e. sending out `GAME_OVER` to both clients) or if a client sends a `DISCONNECT`. If the client sends a `DISCONNECT`, the server only cleans up the socket for that particular client, making sure it is free for a new (or even just the same) client to connect to the server.
